# C++ Lambda Expression Industry Standards

In industrial C++ codebases, choices are driven by two main factors: **zero-cost abstractions (performance)** and **readability/maintainability**.

---

### Category 1: Structure & Signature

* **Most Common:** **Implicit Return Type Lambda**
  ```cpp
  auto add = [](int a, int b) { return a + b; };
  ```
  * **Why:** If a lambda has a single return statement, or all return paths result in the exact same type, the compiler deduces it effortlessly. Programmers omit `-> return-type` to keep code clean.
* **Industry Standard:** **Implicit Return Type**, supplemented by the **Trailing Return Type** *only* when returning references, or handling complex conditional branches where deduction might fail.
* **Avoid / Use Sparingly:** **IIFEs (Immediately Invoked Lambdas)**. They are excellent for initializing a `const` variable via complex logic, but overusing them inside long expressions can make code deeply nested and highly unreadable.

---

### Category 2: Capture Mechanism

* **Most Common:** **Specific Value/Reference Capture** `[x, &y]` and **Empty Capture** `[]`.
  ```cpp
  int threshold = 10;
  std::string log_msg = "Found: ";
  auto check = [threshold, &log_msg](int val) { ... };
  ```
  * **Why:** Explicitly naming your captures is a major industry best practice. It acts as documentation, telling anyone reading the code exactly what external data this block depends on.
* **Industry Standard:** **Explicit capturing**, and **Generalized/Init-Capture (`[ptr = std::move(p)]`)** for passing move-only types like `std::unique_ptr`.
* **Avoid / Banned in Style Guides:** **Default captures like `[=]` and `[&]`**.
  * *Why `[=]` is risky:* It can silently copy large, expensive structures without you realizing it. Even worse, inside a class member function, `[=]` captures the `this` pointer by value, **not** the class data members. This often leads to dangling pointers and undefined behavior if the lambda outlives the parent object.

---

### Category 3: Evaluation Mode & Features

* **Most Common:** **Standard (C++11 style) Mono-morphic Lambdas** and **Generic Lambdas (C++14)**.
  ```cpp
  auto print = [](const auto& item) { std::cout << item << '\n'; };
  ```
  * **Why:** Generic lambdas (`auto` parameters) are incredibly popular because they allow you to write reusable code (e.g., iterating over a collection where you don't want to type out a massive, ugly `std::unordered_map<K, V>::value_type` iterator signature).
* **Industry Standard:** **Generic Lambdas** for daily tasks. **Explicit Template Lambdas (C++20)** are the gold standard when writing generic library code or when you need to enforce that two `auto` parameters share the *exact* same type (e.g., `[]<typename T>(T a, T b)`).
* **Avoid / Use Sparingly:** Forcing `constexpr` / `consteval` if it isn't needed. Use compile-time evaluation only if the lambda is strictly meant for metaprogramming or compile-time calculations.

---

### Category 4: Storage Mechanism

* **Most Common:** **`auto` Storage**
  ```cpp
  auto dynamic_filter = [](int x) { return x > 0; };
  ```
  * **Why:** Using `auto` retains the unique closure type generated by the compiler. This allows the compiler to inline the entire lambda expression directly into your loops or algorithms, achieving 100% maximum performance.
* **Industry Standard:** **`auto`** is the absolute rule for local lambdas and pass-by-template parameters (like passing a predicate to `std::sort`). 
* **Avoid / Use Cautiously:** **`std::function`**. 
  * *Why:* `std::function` introduces **type erasure**, which often forces dynamic memory allocation (heap allocation) and runtime pointer chasing (vtable lookups). It completely destroys the compiler’s ability to inline the code. Use `std::function` *only* when you absolutely need to store lambdas in an array/container or pass them through non-templated API boundaries (like callback systems).

---

### Summary Checklist for Production Code
If you are writing production-grade C++, strive to write your lambdas like this:
1. Prefer **`auto`** to store or pass it.
2. Be **explicit** in your capture lists (`[x, &y]`), never lazy (`[=]`).
3. Use **`const auto&`** in the parameters if the data type is heavy or generic.
